# 自动化测试用例标准

> 本标准用于标记用例的自动化适用性，指导哪些用例适合转化为自动化脚本。

---

## 一、自动化适用性评估

### 1.1 适合自动化的用例特征

| 特征 | 说明 | 自动化收益 |
|------|------|-----------|
| 高频执行 | 每次发版必运行 | 节省大量人工 |
| 稳定不变 | 业务规则少变化 | 维护成本低 |
| 数据确定 | 输入输出可预期 | 断言容易编写 |
| 耗时较长 | 手工执行 > 5分钟 | 显著提速 |
| 多版本回归 | 需要多版本兼容测试 | 覆盖全面 |

### 1.2 不适合自动化的用例特征

| 特征 | 说明 | 自动化成本 |
|------|------|-----------|
| 低频执行 | 半年以上执行一次 | 投入产出比低 |
| 频繁变化 | 业务逻辑经常调整 | 维护成本高 |
| 探索性测试 | 无明确预期结果 | 无法自动化 |
| 需要人工判断 | 如UI美观、体验 | 不适合自动化 |
| 依赖外部系统 | 无法完全可控 | 不稳定 |

## 二、自动化用例设计原则

### 2.1 用例独立性

```
原则：
- 每个用例独立运行，不依赖其他用例
- 用例执行顺序不影响结果
- 每个用例有自己的前置准备和清理

反例：
❌ 用例A登录 → 用例B验证订单（依赖A的登录状态）
✓ 用例A独立完成登录验证
✓ 用例B独立完成登录验证

原因：并行执行时依赖会导致失败
```

### 2.2 数据可控性

```
原则：
- 测试数据在用例内部准备和清理
- 使用唯一标识避免数据冲突
- 避免使用生产环境的真实数据

数据准备方式：
1. 随机生成（推荐）：test_user_{timestamp}_{random}
2. 从数据池获取：提前插入，用例执行后还原
3. Mock服务：外部依赖用Mock替代
```

### 2.3 断言明确性

```
原则：
- 每个用例有明确的pass/fail标准
- 断言信息清晰，失败时易定位问题

良好断言：
✓ assert_equal(response.code, 200, "响应状态码正确")
✓ assert_in("success", response.body, "响应包含成功标识")
✓ assert_equal(len(items), 3, "返回3条数据")

不良断言：
✘ assert_true(response.ok)  # 信息不足
✘ assert(response)  # 无法区分失败原因
```

### 2.4 用例原子性

```
原则：
- 一个用例只验证一个功能点
- 避免用例过于复杂

拆分标准：
- 功能点独立即可独立运行
- 一个前置条件失败不应影响其他用例
- 验证逻辑清晰，不涉及多重判断
```

## 三、自动化标记规范

### 3.1 自动化适用性标记

在 XMind 用例标题中增加标记：

| 标记 | 含义 | 说明 |
|------|------|------|
| 【可自动化】 | 适合做自动化 | 优先纳入自动化套件 |
| 【人工优先】 | 不适合自动化 | 保持手工测试 |
| 【半自动】 | 部分可自动化 | 提取可自动化的步骤 |

### 3.2 自动化优先级

| 优先级 | 标记 | 标准 |
|--------|------|------|
| P0-A | 【可自动化-P0】 | 冒烟测试用例、核心路径 |
| P1-A | 【可自动化-P1】 | 重要功能、频繁回归 |
| P2-A | 【可自动化-P2】 | 一般功能、低频回归 |

## 四、自动化用例转换模板

### 4.1 API 自动化用例

```
【可自动化-P0】POST_user_create_正常创建用户

# 自动化脚本要点
- 前置：清理可能冲突的数据
- 请求：POST /api/users with body

- 断言：response.body.id is not None
- 清理：删除创建的测试数据
```

```
【可自动化-P1】用户登录_输入正确账号密码_登录成功

- 断言：URL跳转到首页
- 断言：页面显示用户昵称
- 清理：退出登录
```

## 五、自动化覆盖率估算

### 5.1 按测试类型

| 测试类型 | 自动化可行比例 | 说明 |
|---------|--------------|------|
| 功能测试（API） | 70-80% | 接口测试易于自动化 |
| 功能测试（UI） | 30-50% | 复杂UI维护成本高 |
| 回归测试 | 60-80% | 高频执行，自动化价值高 |
| 冒烟测试 | 80-90% | 核心路径，自动化价值高 |
| 边界测试 | 80-90% | 规则稳定，易自动化 |
| 探索性测试 | 0% | 不适合自动化 |

### 5.2 自动化收益评估公式

```
自动化收益 = (手工执行时间 × 执行频率 × 人工成本) - 自动化开发维护成本

判断标准：
- 年度节省时间 > 开发维护成本 → 值得自动化
- 执行频率 > 10次/年 → 可考虑自动化
- 单次执行时间 > 30分钟 → 强烈建议自动化
```

## 六、用例命名与结构

### 6.1 自动化用例命名

```
【可自动化-P0】模块_功能点_测试条件

示例：
【可自动化-P0】用户管理_创建用户_必填项完整_成功
【可自动化-P1】订单管理_订单查询_日期范围筛选_成功
【人工优先】用户体验_页面布局_不同分辨率_人工验证
```

### 6.2 自动化用例结构

```
前置条件：
  - 测试数据：user_test_001
  - 系统状态：已登录

步骤：
  1. 调用POST /api/users，body={...}
  2. 记录返回的user_id

预期结果：
  1. HTTP 201 Created
  2. 响应包含 user_id
  3. 数据库可查询到该用户

自动化备注：
  - 可使用 @pytest.fixture 管理测试数据
  - 建议使用 allure 记录执行日志
```

## 七、质量检查清单

- [ ] 用例是否独立，无隐式依赖
- [ ] 测试数据是否可控可清理
- [ ] 断言是否明确，失败信息是否有用
- [ ] 用例是否原子，一个用例只测一件事
- [ ] 自动化标记是否正确（P0/P1/P2）
- [ ] 是否区分【可自动化】和【人工优先】
- [ ] 预期自动化覆盖率是否合理
